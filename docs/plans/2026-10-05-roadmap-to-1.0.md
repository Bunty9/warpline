# warpline roadmap: 0.2.1 to 1.0

Date: 2026-10-05. Companion to `adoption-report.md`. Section 3 of that report defines the use-case names, and section 5 defines the gap IDs (G#).

**Conventions**
- Effort: S ≤ 2 days, M ≈ 1 week, L ≥ 2 weeks, for one maintainer.
- Leverage: use cases unblocked ÷ effort weight (S=1, M=3, L=6). Within each release, items are ordered by leverage, subject to their dependencies.
- **Brk** marks a breaking change: API, WIT, behaviour or schema backfill.
- Use-case short names: **SaaS hooks**, **Commerce hooks**, **Agent tools**, **Policy engine**, **Workflow code steps**, **LLM code execution**, **Webhook transforms**, **Template rendering**, **In-house FaaS**, **CMS plugins**.

## Change from the suggested grouping

I inserted **0.2.2 "production defaults"** between 0.2.1 and 0.3. Four of the highest-leverage fixes are S or M, non-breaking, and touch neither the API nor the WIT:
- durable KV in the binary
- admission knobs
- real health checks
- the auth circuit breaker

Holding them for the 0.3 WIT bump would keep the shipped binary unsafe for production for another 5–6 weeks for no reason.

I also moved **wasi:http** from "standards" (0.3) to **0.5**, for three reasons:
- It is L.
- It depends on the egress-policy refactor.
- P3 guest toolchains are still "in progress", and 0.3.2 lands 2026-10-13.

Waiting lets one release ship p2 and p3 together through `wasmtime-wasi-http`, which carries both. 0.3 is therefore "guest contract and DX", not "standards".

**Calendar constraint:** wasmtime 49 support ends around 2026-11-20. The release that ships after that date must be on wasmtime 50 or 51.

## The 5 highest-leverage items

| # | Item | Release | Effort | Unblocks | Why |
|---|---|---|---|---|---|
| 1 | **Admission knobs**: `WARPLINE_MEMORY_BUDGET_BYTES`, `WARPLINE_MAX_IN_FLIGHT_PER_TENANT`, documented sizing (G2) | 0.2.2 | S | All 9 production use cases | The binary currently caps at about 16 concurrent invocations on any machine and offers no way to raise it. |
| 2 | **Durable KV in the binary**: `PgKv` promoted into `warpline_core::pg`, used by default when `DATABASE_URL` is set (G1) | 0.2.2 | S–M | SaaS hooks, Commerce hooks, Agent tools, Policy engine, Workflow code steps, Webhook transforms, Template rendering, In-house FaaS | Guest state is currently lost on every restart. The code already exists in `examples/storefront/app/src/kv.rs`. |
| 3 | **WIT `warpline:host@0.2.0`, part 1**: `http-out` request headers plus a fallible `handle -> result<list<u8>, string>` (G4, G5) | 0.3 | S–M | SaaS hooks, Agent tools, Workflow code steps, LLM code execution, Webhook transforms, In-house FaaS | Without headers a guest cannot call any authenticated API. Cheap now, expensive after adoption. |
| 4 | **Guest DX core**: WIT published via `wkg`, a `warpline-guest` crate, TS (jco) and Python (componentize-py) templates, and a CI language matrix (G8) | 0.3 | M | All top 9 (gap J) | JS/Python is the most frequent blocker across the top use cases. |

The next tier: the OpenAPI spec with TS and Python clients (C2), and `warpline-tower`/`warpline-axum` (C3). They unblock stacks rather than use cases, so they lead 0.4.

## 0.2.1: security and binaries (in progress)

**Goal:** close the wasmtime advisories and make warpline installable without a Rust toolchain.

| ID | Item | Effort | Brk | Unblocks | Deps |
|---|---|---|---|---|---|
| R1 | wasmtime 49.0.2 (RUSTSEC-2026-0321..0327) | S | No | All (security) | — |
| R2 | 4-target tarballs, `SHA256SUMS`, build-provenance attestations, binstall metadata, GHCR amd64/arm64 image built from the tarballs | M | No | Trial for every use case; non-Rust stacks via the image | — |

**Exit criteria:**
- The `v0.2.1` tag produces all four archives plus `SHA256SUMS`, and `gh attestation verify` passes on each archive.
- `cargo binstall --dry-run warpline-host` resolves the archive.
- `docker pull ghcr.io/bunty9/warpline:0.2.1` runs on both architectures.
- `cargo deny check advisories` is clean.

## 0.2.2: production defaults (new; non-breaking)

**Goal:** the shipped binary is safe to run in production on one box.

| ID | Item | Effort | Brk | Unblocks | Deps |
|---|---|---|---|---|---|

| A3 | Auth circuit breaker plus singleflight per key hash, returning 503 with `Retry-After` (G12, Known issue 1) | S | No | All | — |
| A4 | `PgKv` in `warpline_core::pg` with its own small pool and per-query timeout, default in the binary (G1) | S–M | Behaviour: KV now persists | 8 (see top 5) | — |
| A5 | `SECURITY.md`: advisory tracking SLA, wasmtime bump cadence. CI job that tries the next wasmtime major monthly. `ci.yml` SHA pins. Remove the "1800x" claim. | S | No | All (trust) | — |
| A6 | Make the DB `functions` table the GC root; add `warpline-control verify` (Known issue 2) | M | No | All; prerequisite for versions (D2) | — |

**Exit criteria:**
- A restart keeps KV data (integration test).
- At default caps, `memory_budget / 64 MiB` concurrency is configurable and documented.
- `/readyz` fails while Postgres is down, and a test checks that auth fails fast during a DB outage.
- GC never deletes a blob that a `functions` row references (regression test).

## 0.4: stack integrations

**Goal:** every popular host stack has a documented integration of 30 lines or fewer, and the control plane can be operated without SQL.

Before starting, re-scope this release with the results of the demand test.

| ID | Item | Effort | Brk | Unblocks | Deps |
|---|---|---|---|---|---|
| C1 | **Admin API completeness**: list tenants, usage, list and delete functions, list/revoke/rotate keys; **key scopes** (`invoke`, `publish`, `admin`); durable `audit_log` (G11) | M | **Yes**: existing keys backfilled to `invoke+publish` | All (operability); SaaS hooks and Agent tools especially (leaked client keys can't publish) | A6 |
| C2 | **OpenAPI 3.1** for both services; `@warpline/client` (npm) and `warpline` (PyPI) with typed errors and retry on 429/503; FastAPI, Django, Express and Fastify examples | M | No | All, for Node and Python stacks; Go, Java, .NET, Ruby, PHP and Elixir via generated clients | C1 |
| C3 | **`warpline-tower` + `warpline-axum`**: `Authenticate` trait extracted from `pg::Authenticator`; binaries take `Arc<dyn Authenticate>`; examples for actix, Poem and Salvo | S + M | No (new crates; the trait is additive) | All, for Rust stacks | — |
| C4 | Helm chart (single replica, probes, ServiceMonitor, PVC), systemd unit, Render and Railway templates | M | No | In-house FaaS; all self-hosters | A2 |
| C5 | **OTel**: per-invoke span in core with child spans for compile, instantiate, kv and fetch; `traceparent` injected into `http-out`; metrics moved into core behind a feature; `x-warpline-invocation-id`; `MeterSink` outcome enum; Grafana dashboard | M | `MeterSink` signature change → **Yes** for implementors | SaaS hooks, Commerce hooks, Policy engine, In-house FaaS (gap O) | — |
| C6 | MCP adapter example: `tools/list` from per-function JSON-schema metadata, `tools/call` mapped to `invoke` | S–M | No | Agent tools, LLM code execution | B1, B3 |

**Goal:** run standard `wasi:http` components and run N hosts behind a load balancer, with versioned deploys.

|---|---|---|---|---|---|
| D1 | Cron trigger: `schedules` table, `SELECT … FOR UPDATE SKIP LOCKED`, calls `invoke` | M | No | SaaS hooks, Workflow code steps, Template rendering, In-house FaaS | A6 |
| D2 | **Versions, deployments, rollback, canary weights**; retention-aware GC | M–L | Pointer format (reader stays compatible) | Commerce hooks, Policy engine, SaaS hooks, In-house FaaS | A6, C1 |
| D3 | Pooling allocator plus COW; pointer cache and single-flight cold load; HTTP-path bench with a realistic handler at concurrency 1/8/64; admission weighting by observed peak, plus an optional short queue | M | Default behaviour change | All (throughput) | A1, B7 |
| D4 | Per-tenant egress rate, concurrency and byte quotas; per-invocation fetch counters (G17) | M | No | Agent tools, LLM code execution, Workflow code steps (abuse-prone) | — |
| D5 | **`wasi:http` ABI** (p2 and p3 via `wasmtime-wasi-http`): publish-time ABI classification; the egress hook reuses the allowlist and SSRF guard; `Runtime::serve_http`; public webhook routes with HMAC verification | L | No (additive ABI) | In-house FaaS, Webhook transforms, Agent tools; Spin/wasmCloud component portability | B1, D4 (shared egress policy) |
| D6 | **`Registry` trait** plus an S3 implementation (`object_store`): source blobs in S3, `.cwasm` as a node-local cache, name resolution from Postgres, `LISTEN/NOTIFY` invalidation, startup prewarm | L | No (registry is private) | In-house FaaS; multi-node for all | A6, D2, D3 |

- An unmodified Spin/`wasi:http` Rust component deploys and serves, and its outgoing requests obey the allowlist.

- A published bench gives p99 at 64 concurrent invocations through HTTP.

## Do NOT build (YAGNI)

| Item | Why not |
|---|---|
| Native bindings for Java, .NET, Ruby, PHP, Elixir or Go (and napi-rs or PyO3 before the HTTP clients prove demand) | The host-side Component Model ecosystem in those languages is thin. A per-platform binary matrix for one maintainer is too much. The sidecar plus OpenAPI covers them. |
| Running guests through jco or wasmtime-py in the host language | It bypasses every warpline control (caps, admission, egress), which is the product. |
| Kubernetes operator or CRDs; per-function pods | warpline is many tenants in one process. A SpinKube-style per-app CRD fights the design. Helm is enough. |
| Admin web UI | Large security surface (admin token). The CLI plus Grafana cover it. |
| Non-tokio executor support | Every target framework runs on tokio. L effort for no users. |
| `Store` or instance reuse across requests | It breaks per-request isolation. The pooling allocator gives the speed safely. |
| proxy-wasm ABI, DB-UDF scalar ABI, game-mod per-tick worlds | Poor-fit use cases (gateway, UDF, mods). Each needs a different ABI. |
| `wasi:keyvalue`, `wasi:config` or `wasi:logging` as the primary contract | Phase 2 or 1 (verified). Adapters only after Phase 3 or on a concrete request. |
| A custom streaming ABI | WASI P3 `stream<T>` solves it; arrive there through D5. |
| Queue triggers for several brokers | Do one (NATS or Redis streams), after cron, on request. |
| Guest SQL import | It raises the tenancy-isolation risk. KV v2 plus `http-out` covers most needs. |
| Durable or long-running execution, GPU, full-OS agent sandboxes | That is the Salesforce Functions failure mode, and E2B, Modal and Golem's territory. |
| Hyperlight backend before 1.0 | Its own repo says it is not production-grade. Revisit after 1.0. |
| cargo-dist migration; musl, Windows, Homebrew, Nix, AUR, Scoop, curl\|sh | Hand-rolled `release.yml` already does it, with hardening. Those targets are untested or Tier 3. Add on request. |
| Distributed per-tenant limiter across nodes | Document per-node semantics until a multi-node user needs exact global caps. |
| Marketing cost comparisons ("1800x") | Not credible (PROGRESS.md says so). |
